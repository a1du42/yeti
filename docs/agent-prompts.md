# Промпты для дальнейшей работы

Эти шаблоны предназначены для ИИ-агента разработки. Они не описывают встроенного помощника внутри YETI STREAM. Подставлять только информацию, относящуюся к задаче; секреты и персональные данные в промпты не включать.

## Универсальная задача

```text
Работай в проекте YETI STREAM. Сначала прочитай AGENTS.md, README.md,
DESIGN.md, docs/decisions.md и документы, относящиеся к задаче.

Задача: [конкретный результат].
Текущий этап: [документация / реализация явно разрешённой функции].
Зона: [/, /app, /admin или /partners].
Границы: [что входит].
Критерии готовности: [наблюдаемое поведение или артефакт].

Проверь существующие файлы и diff. Назови существенные предположения.
Если неизвестное меняет бизнес-логику, доступ, деньги, данные или интеграцию,
задай короткий вопрос до зависимой части работы и продолжай независимое.
Рутинные решения, уже описанные в проекте, принимай самостоятельно.

Следуй общей дизайн-системе. Не выдумывай услуги, тарифы, проценты и сроки.
Не создавай приложение, если задача остаётся документационной.
Не пиши автотесты и не устанавливай тестовую инфраструктуру.
После работы проверь результат допустимым способом, обнови документы
и сообщи, что изменено, что проверено и что осталось открытым.
```

## Проектирование нового экрана

```text
Подготовь спецификацию экрана [название] для зоны [путь]. Код не писать.
Прочитай docs/product.md, docs/design/foundations.md, components.md,
screens.md, content.md и motion.md. Используй ui-ux-pro-max и hallmark
в пределах продуктового интерфейса, Motion-плагин для спорных переходов.

Опиши главную задачу, содержание в порядке важности, основное действие,
desktop/mobile-компоновку, данные и границы доступа. Укажи состояния:
загрузка, результат, пустой список, пустой поиск, ошибка, повтор,
потеря сети и недоступность действия. Неизвестные правила пометь открытыми.

Для справки используй ? рядом с названием раздела. Текст объясняет,
что сделать и что получить, без названий ролей. Критичные условия видны
сразу. Привяжи элементы к существующим токенам и компонентам.
Каждый переход включая задержки укладывается в 400 мс и имеет
вариант reduced motion. Обнови спецификацию и журнал решений.
```

## Выбор архитектуры перед первым кодом

```text
Разрешена подготовка решения по стеку, установка пока не требуется.
Прочитай docs/engineering.md и открытые вопросы docs/decisions.md.
Изучи существующий проект. Сопоставь требования размещения, авторизации,
источника услуг, частоты обновления и расчётов. Уточни только то,
без чего нельзя принять обоснованное решение.

Предложи основной вариант и одну разумную альтернативу. Объясни выбор
через стоимость поддержки, скорость, доступность и структуру данных.
Сохрани короткое архитектурное решение; не выдавай предложенный стек
за ранее утверждённый. Не устанавливай зависимости и не создавай маршруты
до задачи реализации. Автотесты пока отложены.
```

## Реализация согласованной функции

```text
Реализуй [функция] по [путь к согласованной спецификации]. Эта задача
явно разрешает код только для указанного объёма. Сначала проверь,
что стек и блокирующие бизнес-правила определены; иначе задай вопрос.

Используй существующие компоненты и семантические tokens.css.
Асинхронность должна убирать блокировки, а не нарушать порядок операций.
Независимые чтения можно распараллелить с ограничением конкуренции.
Предусмотри отмену устаревших запросов, защиту от гонок, идемпотентность
изменяющих операций и честные состояния ошибок. Не подтверждай платёж,
заказ или выплату оптимистически.

Не меняй корневые пути, бренд и общую структуру без причины в задаче.
Не пиши автотесты. Пройди основной сценарий и восстановление вручную;
для UI проверь клавиатуру, обе темы, затронутые ширины и reduced motion.
Существующие сборку / typecheck / lint используй по необходимости.
Отчитайся только о проведённых проверках и обнови документацию.
```

## Проверка справочных текстов

```text
Проверь тексты [экран/файл] по docs/design/content.md.
У каждого полезного пояснения должен быть ? рядом с названием раздела.
Tooltip отвечает на «что здесь сделать» и «как получить результат».
Убери упоминания аудитории, ролей, административной кухни и технологий.
Не скрывай обязательные условия, стоимость, ошибки и последствия.
Проверь короткую длину, русский язык и соответствие реализованной функции.
Если функция не подтверждена, пометь вопрос, а не сочиняй обещание.
```

## Исправление ошибки или замедления

```text
Исследуй [симптом] и воспроизведи его в доступной среде.
Прочитай применимые инструкции, проверь текущий diff и затронутый код.
Определи причину по фактам; не начинай широкий рефакторинг без связи
с симптомом. Для скорости сначала измерь проблемное место.

Сделай минимальное устойчивое исправление. Вручную повтори исходный
сценарий, проверь соседний путь и восстановление после ошибки.
Автотесты и тестовая инфраструктура пока не создаются.
Сообщи причину, изменение, фактическую проверку и оставшиеся ограничения.
```

## Формат завершения

Коротко: результат и затронутые файлы; реально выполненная проверка; нерешённый вопрос, если есть. Не писать «всё работает» после одной правки текста и не объявлять готовым продукт, когда подготовлена только документация.
