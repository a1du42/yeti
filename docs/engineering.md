# Инженерные правила

Действующий стек: Next.js App Router + TypeScript, PostgreSQL, Drizzle и Better Auth; локальная почта — Mailpit. Структура, команды и настройки заданы в [development.md](development.md), границы — в [decisions.md](decisions.md). Текущая реализация включает авторизацию, оболочку `/app` и отдельно разрешённое пополнение через Heleket в USD. Остальные бизнес-функции добавляются отдельными задачами. [Контракт оплаты](payments.md).

## Границы

Четыре корневые зоны имеют независимую маршрутизацию, навигацию и проверку доступа. Дизайн-токены, UI-примитивы и общие форматтеры переиспользуются. Клиентская видимость пункта меню не является авторизацией.

Каждый объект и действие проверяются на сервере с учётом текущей учётной записи и разрешений. При отсутствии доступа не раскрывать чужие данные. Клиент `/app` не получает скрытую административную модель «на всякий случай». Тяжёлый код `/admin` не входит в начальную загрузку `/app`.

Использовать один Next.js-процесс для UI и серверных обработчиков, CSS Modules с `tokens.css`, Radix UI и Phosphor Regular. По умолчанию применять Server Components; интерактивные границы выделять явно. Не устанавливать одновременно несколько систем компонентов или управления состоянием. Изменение стека фиксировать отдельным решением с причиной и альтернативой.

## Асинхронность

| Ситуация | Подход |
| --- | --- |
| Независимые блоки обзора | Параллельная загрузка; ошибки изолированы по блоку |
| Расчёт зависит от параметров | Сначала валидация; debounce, отмена предыдущего запроса, проверка версии результата |
| Создание заказа | Последовательность расчёт → подтверждение → создание; идентификатор идемпотентности |
| Долгая операция | Фоновая задача с идентификатором и проверяемым состоянием |
| Большой расчёт на клиенте | Worker при доказанной необходимости; async без Worker не разгружает CPU |
| Частые статусы | SSE или polling после оценки источника и частоты; WebSocket только при двусторонней необходимости |

`Promise.all` уместен для независимых обязательных результатов с общей ошибкой, `allSettled` для независимых секций с частичным успехом. Не распараллеливать зависимые мутации и не создавать неограниченный fan-out. Ограничить конкуренцию в зависимости от лимитов источника.

Все запросы имеют управляемое время ожидания, отмену при устаревании и защиту от гонок. Побеждает ответ на последнюю актуальную версию параметров, а не последний пришедший ответ. Отмена клиентского ожидания не равна отмене серверной операции.

Автоповторы только для безопасных чтений или подтверждённо идемпотентных операций; ограниченное число попыток, backoff с jitter и учёт Retry-After. Не повторять бесконечно, не ретраить ошибки валидации и отказ в доступе. Timeout создания требует сверки по ключу операции до повторной отправки.

## Состояние и данные

Локальное UI-состояние живёт возле компонента. Серверные данные имеют определённую стратегию кэширования, инвалидирования и свежести. Данные разных учётных записей не смешиваются; при смене аккаунта / выходе очистить защищённый клиентский кэш.

Фильтры и пагинация могут быть в URL; секреты и персональные сведения там не хранятся. Отображать дату последнего достоверного обновления при деградации. Не заменять известный ответ пустой таблицей во время фонового обновления.

Оптимизм подходит для обратимых предпочтений, если есть откат и понятная ошибка. Создание оплачиваемого заказа, подтверждение оплаты, начисление, выплата, удаление и изменение доступа не становятся успешными до ответа сервера. Двойное нажатие и повтор доставки события не должны дублировать эффект.

Деньги, статусы оплаты и исполнения разделены. Подтверждения финансовых событий приходят от проверенного серверного источника, а не только со страницы возврата после оплаты. Транзакции и идемпотентность выбираются после определения модели. Не обещать «ровно один раз» без учёта повторной доставки.

## Быстрый интерфейс

- Разделять загрузку кода по маршрутам и тяжёлым функциям. Аналитику и большие редакторы загружать по необходимости.
- Не блокировать критичный контент необязательными виджетами. Skeleton резервирует геометрию, известные данные остаются видимыми.
- Локальные WOFF2 с кириллицей, только нужные веса. Preload используемых на текущей странице начертаний в head до основных стилей; загрузка начинается при открытии, без ожидания JavaScript или действия. Не загружать шрифты других маршрутов. Сохранять font-display: swap и fallback, не блокировать интерфейс ожиданием шрифтов.
- Сохранять размеры изображений и логотипа. Оптимизировать медиа; исходный SVG не превращать в тяжёлый bitmap для интерфейса.
- Списки ограничивать серверной пагинацией / окнами. Виртуализацию применять после измерения и проверки клавиатуры, поиска и чтения скринридером.
- Не выполнять тяжёлую синхронную работу в обработчиках ввода. Не менять React state на каждом кадре для движения.
- Предпочитать индексированные запросы и необходимый набор полей. Не загружать весь каталог, журнал или все операции ради одного экрана.
- Не прятать реальные задержки непрерывной анимацией. Интерфейс принимает следующее допустимое действие сразу.

Цели после появления приложения: Core Web Vitals на p75 LCP ≤2,5 с, INP ≤200 мс, CLS ≤0,1. Обратная связь на локальное нажатие начинается в пределах 100 мс. До замера на согласованном устройстве и сети эти числа являются целями, а не обещанной производительностью.

Размер бандла, бюджет API и частота обновлений определяются по объёму данных и измерениям; не закреплять произвольные пределы без измерений. Lighthouse является диагностикой лабораторного запуска, а не доказательством полевых показателей.

## Доступ и наблюдаемость

Проверять входные данные и права на сервере. Better Auth использует сессии в PostgreSQL, HttpOnly cookie и Secure в production; cookie cache сессий отключён. Сохранять CSRF/trusted origins и проверять собственника данных в каждом обработчике, а не только layout. Секреты БД/SMTP/Better Auth не помещать в `NEXT_PUBLIC_*`. Структурированные журналы не содержат паролей, токенов, полного платёжного содержимого и лишних персональных данных.

Email подтверждается до входа; пароль — 15–128 Unicode code points без обрезки и нормализации. Поддерживаемый custom hash/verify Better Auth использует асинхронный `node:crypto.scrypt` (`N=131072`, `r=8`, `p=1`, соль 16 байт) и `timingSafeEqual`; стандартный хеш Better Auth заменён из-за NFKC-нормализации. Сессия скользящая на 7 дней с обновлением раз в сутки; ссылки подтверждения и сброса — 1 час. После сброса отзываются все сессии. Проектные лимиты Better Auth с хранением в БД: 5 попыток входа/мин, 3 запроса регистрации/восстановления/подтверждения письма/мин на endpoint.

`AUTH_TRUSTED_PROXY_HEADER` опционален: без него все запросы используют общий loopback-ключ rate limit, что подходит для консервативного локального режима. В production настройка допустима только при закрытом прямом доступе к origin и доверенном proxy, который перезаписывает указанный заголовок. Не доверять произвольному `X-Forwarded-For` из клиентского запроса.

GET `/app/auth/reset` переносит токен в HttpOnly cookie с path `/api/auth/reset-password`, SameSite Strict и Secure на HTTPS, затем очищает URL перенаправлением; HTTP — только локально. Действительность и одноразовость проверяет Better Auth при смене пароля. JWT подтверждения email дополнительно ограничен одноразовым SHA-256-состоянием в `verification`. SMTP отправляется через Next.js `after()` после публичного ответа: ответ означает принятие запроса, не доставку. Устойчивой очереди и автоматических повторов нет; при сбое — безопасный журнал без получателя/токена и ручной повтор запроса.

Для асинхронной операции нужны correlation ID, время, состояние и причина ошибки. Пользователю показывается безопасное понятное сообщение. В журнале изменений сохраняются автор, объект, действие, время и подтверждённый результат согласно будущей политике хранения.

## Проверка без автотестов

Действует временный запрет из [AGENTS.md](../AGENTS.md): не писать автоматические тесты и не добавлять тестовую инфраструктуру. После задачи вручную пройти главный сценарий, ошибку и восстановление; при затрагивании интерфейса проверить обе темы, нужные ширины, клавиатуру и reduced motion.

Если уже есть линтер, typecheck и сборка, выполнять релевантные команды. Разовая проверка целостности документов допустима. В отчёте привести реально выполненные проверки и ограничения среды. Не отмечать тест, браузер или измерение пройденными, если они не запускались.

## Конфигурация способов входа

Контракт — [auth.md](design/auth.md#доступность-и-расположение-сервисов). Определять доступность каждого провайдера на сервере по полному комплекту обязательных настроек. Клиенту передавать только признаки доступности, без ключей и секретов. Отключённый сервис не выводить и не разрешать при прямом старте OAuth/callback. Витрина использует демонстрационные флаги без реальных интеграций.

Подключены email и Google; Яндекс ID, Telegram и Kick остаются следующим этапом с ключами. Сейчас их кнопки скрыты и OAuth endpoints не подключены. Нижеследующий контракт применяется при их последующей интеграции, а не означает наличие работающих провайдеров.

Первый успешный внешний вход автоматически создаёт аккаунт и связывает проверенную идентичность провайдера; последующие используют ту же запись. Обеспечить атомарность и уникальность идентичности при параллельных callbacks. Не создавать аккаунт при отказе/ошибке; автоматическая привязка Google при входе требует совпадения подтверждённой с обеих сторон почты. Явное подключение сервиса из настроек требует сессию текущего пользователя и успешный OAuth, допускает другую почту и сохраняет профиль. Идентичность, уже привязанную к другому пользователю, не переносить и аккаунты не объединять. Имя обязательно в обычной email-регистрации; кнопки провайдеров на форме доступа — только во входе.
