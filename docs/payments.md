# Оплата через Heleket

Задание и уточнения пользователя от 2 ноября 2026 года: пополнение баланса в «Профиль → Оплата» (`/app?tab=payment`), все цены и суммы в долларах США (USD). Минимум 1 USD, максимум 1000 USD включительно, шаг 0,01 USD. Комиссия на клиенте; подтверждённая переплата зачисляется в USD. Услуги, списания, выплаты и создание возвратов в это задание не входят.

## Настройка

Текущее окружение, 2 ноября 2026 года: реквизиты пользователя сохранены только в `.env.local`, публичный файл `public/heleket_f3afee8a.html` размещён и домен `a1d.by` подтверждён в кабинете Heleket. Реальный API отвечает `401 / Api not active.`; мерчант ещё не отправлен на модерацию. Heleket требует работающий сайт, активные продукты/услуги и контакты поддержки; их создание выходит за рамки этого задания. До активации `HELEKET_ENABLED=false`. После модерации включить флаг, перезапустить приложение и завершить проверку реального счёта и webhook. Секретный ключ в файл подтверждения домена не входит.

В `.env.local` заполнить серверные переменные:

```dotenv
HELEKET_MERCHANT_ID=
HELEKET_PAYMENT_KEY=
HELEKET_ENABLED=false
HELEKET_MIN_USD=1
HELEKET_MAX_USD=1000
HELEKET_FEE_PAYER=customer
```

Merchant ID и **платёжный** API-ключ берутся из настроек мерчанта Heleket. Ключ выплат не нужен. Секреты не добавлять в чат, репозиторий, URL или `NEXT_PUBLIC_*`. Реальные значения в примере отсутствуют. Пустой либо неверный комплект настроек отключает создание счетов. После настройки мерчанта включить `HELEKET_ENABLED=true` и перезапустить приложение.

`BETTER_AUTH_URL` должен содержать публичный HTTPS-origin приложения. Текущий callback: `https://a1d.by/api/payments/heleket/webhook`. Обычный и успешный возврат ведут на `https://a1d.by/app?tab=payment`. На proxy пропускать POST callback без пользовательской авторизации и без browser challenge, сохраняя защиту остальных маршрутов. Нельзя считать успешный return URL доказательством оплаты.

Применить `npm run db:migrate`, выполнить `npm run build` и перезапустить процесс приложения. Миграция `0001_worried_nuke.sql` создаёт `payment` и `payment_credit`, не изменяет существующие деньги и аккаунты. Вымышленный баланс старого стенда не переносится; баланс нового аккаунта вычисляется как сумма подтверждённых зачислений и равен 0 USD при отсутствии таких записей.

## Протокол и учёт

- Клиент отправляет сумму десятичной строкой и UUID идемпотентности. Сервер повторно проверяет диапазон, точность, сессию, подтверждение email, Origin и собственника каждого счёта. Валюта всегда задаётся сервером как USD.
- До обращения к провайдеру сохраняется идентификатор счёта. В Heleket он передаётся как `order_id`: повтор после timeout использует тот же идентификатор. Создание ограничено пятью новыми счетами в минуту на аккаунт; все пользовательские POST оплаты вместе — двадцатью запросами в минуту. Лимиты хранятся в PostgreSQL.
- Для счёта передаются `subtract=100`, `accuracy_payment_percent=0`, `is_payment_multiple=true`: комиссия на клиенте, доплата при неполной оплате разрешена. Сумму в выбранной криптовалюте и комиссию показывает Heleket перед переводом; произвольный процент комиссии в интерфейсе не обещается.
- Webhook проверяет MD5-подпись по протоколу Heleket с постоянным временем сравнения, затем сервер дополнительно получает `payment/info`. Сверяются `order_id`, UUID, исходная сумма и USD. Поддельное уведомление, недостаточная сумма, AML-проверка и простой переход на return URL не создают зачисление.
- Только финальные `paid` и `paid_over` создают зачисление. В транзакции блокируется строка счёта, записывается положительная разница с прежней подтверждённой суммой и обновляется счёт. Неизменяемые записи `payment_credit` имеют уникальную пару «счёт + подтверждённая общая сумма». Повтор webhook, ручная сверка и параллельные запросы не дублируют баланс. Более поздняя подтверждённая переплата добавляет только разницу.
- При `paid` зачисляется исходная сумма счёта. При `paid_over` превышение `payment_amount` над требуемой `payer_amount` переводится в USD через `payer_amount_exchange_rate` этого USD-счёта. Требуемая сумма включает комиссию клиента, поэтому сама комиссия не попадает на баланс. Расчёт выполняется целыми BigInt с масштабом 18 знаков, результат хранится в центах; доли цента отбрасываются. Неполные данные или аномально крупная сумма блокируют зачисление до сверки. Переплата может увеличить зачисление выше лимита 1000 USD: лимит относится к созданию счёта.
- Timeout провайдера — 12 секунд, клиентского ожидания — 25 секунд. Отмена ожидания не отменяет счёт. В истории можно обновить статус; для неподтверждённого создания это повторяет идемпотентное создание с тем же `order_id`. При ошибке последняя полученная история и баланс сохраняются. Автоматического бесконечного polling и повторов нет.
- В истории показаны последние 50 счетов. Баланс учитывает все зачисления. Даты отображаются в часовом поясе браузера. Уведомление о новом зачислении появляется снизу по центру без переноса фокуса.

Полученные статусы возврата показываются, но автоматическое списание уже зачисленного баланса и финансовая сверка возвратов не реализованы. До отдельной задачи не инициировать возвраты оплаченных счетов через кабинет/API Heleket без ручного урегулирования баланса. AML-блокировка после зачисления также требует отдельной сверки. Устойчивой фоновой очереди нет: при отказе обработчик возвращает ошибку, восстановление возможно повторной доставкой провайдера или ручным обновлением статуса.

## Ручная проверка перед включением

Проверить границы 1 и 1000 USD, ввод ниже/выше диапазона и вставку, пустоту, 1,01 USD и ошибку 1,001 USD; клавиатуру и обе темы при 320/768/1024 px. Без ключей кнопка недоступна с объяснением. Без сессии API не раскрывает баланс; чужой ID счёта недоступен; POST с чужим Origin запрещён.

С настроенным мерчантом: создать счёт, проверить сумму и комиссию на стороне Heleket, вернуться без оплаты — баланс не меняется. Затем подтвердить реальную оплату, проверить webhook и зачисление, повторить уведомление и ручную сверку — баланс не увеличивается повторно. Отдельно проверить переплату, недоплату, AML-проверку, недоступность провайдера и повтор после timeout. Успешная сборка и локальная имитация ответов не заменяют проверку реального провайдера.
