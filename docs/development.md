# Разработка YETI STREAM

Яндекс ID использует российские OAuth endpoints: `https://oauth.yandex.ru/authorize` и `https://oauth.yandex.ru/token`. Это направляет вход через российский домен Яндекс Паспорта вместо `.com`; callback приложения — `https://a1d.by/api/auth/callback/yandex`.

Google подключён через Better Auth при наличии обоих серверных значений `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET`. Кнопка с фирменным знаком доступна только во входе. Callback текущего окружения: `https://a1d.by/api/auth/callback/google`; этот адрес необходимо зарегистрировать в Google Cloud. Используются только openid/email/profile, PKCE S256, одноразовый state и nonce; подпись ID token, issuer, audience, exp и nonce проверяются сервером через Google JWKS. Дополнительный email и пароль не запрашиваются; Google объединяется с существующим аккаунтом при совпадении подтверждённой с обеих сторон почты. Часовой пояс браузера передаётся в состоянии OAuth и проверяется; при неизвестной зоне хранится пустое значение без подстановки города. Токены провайдера шифруются на сервере.

Действующее решение от 2 ноября 2026 года. Текущий этап — настоящая email-авторизация на `/app/auth` и защищённая оболочка `/app` с двумя тестовыми разделами, данными и меню текущего пользователя. Корневой `/` остаётся пустым; `/admin`, `/partners`, услуги и заказы в этот этап не входят. Отдельное задание разрешает пополнение баланса через Heleket; [настройка](payments.md). [Общие правила](../AGENTS.md) и [инженерные требования](engineering.md) обязательны.

## Стек и границы

| Часть | Выбор |
| --- | --- |
| Приложение и сервер | Next.js App Router, React, TypeScript; Node.js runtime |
| Данные | PostgreSQL, Drizzle ORM и SQL-миграции Drizzle |
| Авторизация | Better Auth с Drizzle adapter, серверные сессии в PostgreSQL |
| Почта | SMTP; локально Mailpit, перед production нужен настоящий SMTP-сервис |
| Интерфейс | CSS Modules, канонический `tokens.css`, доступные примитивы Radix UI, Phosphor Regular |
| Локальная инфраструктура | Docker Compose: PostgreSQL и Mailpit |
| Пакеты | npm, зафиксированный `package-lock.json` |

Единое Next.js-приложение выбрано вместо отдельного frontend и backend: на этом этапе достаточно одного процесса с серверными границами. PostgreSQL выбран сразу для реального хранения аккаунтов и сессий; Drizzle сохраняет явную схему и проверяемые миграции. Better Auth отвечает за стандартные процессы доступа вместо собственной криптографии и самодельной модели сессий. CSS Modules используют существующую дизайн-систему без параллельного набора Tailwind-токенов. Версии пакетов фиксируются manifest и lockfile; обновление требует проверки официальной документации и совместимости.

## Структура

`/app?tab=payment` показывает `PaymentPanel`: серверные баланс и историю, создание счёта Heleket, переход на оплату и получение подтверждённых статусов. API: `/api/payments`, `/api/payments/[id]`, `/api/payments/heleket/webhook`. Таблицы `payment` и `payment_credit`; миграция `0001_worried_nuke.sql`. Серверная сессия обязательна для каждого пользовательского запроса, POST дополнительно проверяет Origin. [Настройка Heleket](payments.md).

- `src/app` — маршруты и layouts App Router; `/app/auth` публичен, рабочие экраны `/app` проверяют сессию на сервере.
- `src/components` — общие UI-компоненты и оболочка; CSS Modules находятся рядом с компонентами.
- `src/lib` — серверная конфигурация Better Auth, доступ к данным, почта и общие функции. Серверные модули не импортируются клиентскими компонентами.
- Схема Drizzle и SQL-миграции хранятся в репозитории; настройки мигратора заданы в `drizzle.config.ts`.
- `public` — необходимые статические ресурсы приложения. Архивный `visual-spec.svg/PNG` в сборку не включать.
- `docs/design` и `design-system.html` — самостоятельная документационная витрина; её JavaScript не является серверной или клиентской логикой приложения.

По умолчанию использовать Server Components. `use client` добавлять для интерактивной границы: формы, вкладки, меню, тема. Локальное состояние держать рядом с компонентом; отдельный глобальный state manager без необходимости не устанавливать. Чтение сессии, валидация, запросы к БД и SMTP выполняются сервером. Защищённые данные разных пользователей не кэшировать совместно.

## Локальный запуск

Нужны Node.js ≥22.13.0 согласно `package.json`, npm и работающий Docker Compose. В каталоге проекта:

```powershell
Copy-Item .env.example .env.local
npm install
docker compose up -d
npm run db:migrate
npm run dev
```

Перед запуском заменить `BETTER_AUTH_SECRET` в `.env.local` случайным значением, проверить `BETTER_AUTH_URL`, `DATABASE_URL` и SMTP-настройки из `.env.example`. Секрет можно сгенерировать локально:

```powershell
node -e "process.stdout.write(require('node:crypto').randomBytes(32).toString('base64url'))"
```

Полученное значение записать в `.env.local`, не в чат или документацию. `.env.local` не коммитить. Пример конфигурации предназначен для локальной разработки; production требует собственных реквизитов и HTTPS.

| Адрес / порт | Назначение |
| --- | --- |
| `http://localhost:100/app/auth` | Вход, регистрация и восстановление |
| `http://localhost:100/app` | Защищённое рабочее пространство |
| `localhost:5434` | PostgreSQL с хоста; внутри Compose используется порт 5432 |
| `localhost:1025` | SMTP Mailpit |
| `http://localhost:8025` | Письма регистрации и восстановления в Mailpit |

Mailpit принимает локальные письма и показывает их в браузере, без доставки на реальные адреса. Для проверки регистрации открыть письмо в Mailpit и перейти по ссылке; то же относится к восстановлению пароля. SMTP вызывается через Next.js `after()` после публичного ответа: интерфейс подтверждает принятие запроса, а не доставку письма. При отказе SMTP записывается только безопасное событие `auth_mail_delivery_failed` без адресов и токенов; повторный запрос выполняется вручную. Устойчивой очереди, гарантии доставки и автоматического повторения пока нет. Подтверждение регистрации определяется проверенной ссылкой, а не самим ответом на запрос письма.

## Зависимости инструментов

В корневом `package.json` задан узкий npm override: `@esbuild-kit/core-utils` → `esbuild: ^0.25.12`. Drizzle Kit использует этот пакет через `@esbuild-kit/esm-loader`; без override старая ветка требует esbuild 0.18.20, затронутый [GHSA-67mh-4wv8-2f99](https://github.com/evanw/esbuild/security/advisories/GHSA-67mh-4wv8-2f99). Override разрешает использовать уже совместно установленный esbuild 0.25.12 и не требует понижения Drizzle Kit. Правило действует только на указанную ветку, согласно [контракту npm overrides](https://github.com/npm/cli/blob/latest/docs/lib/content/configuring-npm/package-json.md#overrides); удалить его после перехода upstream на исправленную зависимость и проверки CLI.

После изменения инструментальных зависимостей проверить `npm ls esbuild --all`, `npm audit` и `npm run db:generate`. Генератор без изменения схемы должен сообщить `No schema changes, nothing to migrate`. При сохранённой старой вложенной копии `npm ls` может показать `invalid`; переустанавливать только затронутую сгенерированную зависимость с согласованием lockfile, не удаляя весь `node_modules` при работающем devserver. Не применять `npm audit fix --force` с понижением Drizzle Kit вместо проверки совместимого override.

## Доступ и настройки

- Email подтверждается до входа; новый пароль содержит 15–128 Unicode code points. `src/lib/auth.ts` задаёт поддерживаемые Better Auth custom `hash`/`verify`: асинхронный `node:crypto.scrypt` с `N=131072`, `r=8`, `p=1`, случайной солью 16 байт и сравнением `timingSafeEqual`. Стандартный хеш Better Auth применяет NFKC, поэтому здесь он заменён обработчиком без нормализации. Проверки клиента и сервера согласованы; пароль не обрезать и не писать в журналы. Имя после trim не пустое, не более 120 Unicode code points; IANA-часовой пояс проверяется сервером.
- Сессия хранится на сервере: скользящие 7 дней, обновление раз в сутки, cookie cache отключён. `deferSessionRefresh` оставляет GET и Server Components без записи: клиентский `useSession()` при необходимости выполняет POST `/api/auth/get-session`, обновляя запись и cookie вместе. Cookie — HttpOnly; в production Secure. Использовать защиту CSRF и trusted origins Better Auth; не отключать её ради обхода ошибки конфигурации.
- Ссылки подтверждения email и сброса действуют 1 час. GET `/app/auth/reset` переносит reset token из URL в HttpOnly cookie `yeti-reset` с path `/api/auth/reset-password` и перенаправляет на чистый URL формы. Cookie имеет SameSite Strict и Secure на HTTPS; HTTP допускается только для локального запуска. Обмен не подтверждает действительность токена: срок и одноразовость проверяются Better Auth при смене пароля. После успеха cookie очищается и отзываются все сессии, автоматического входа нет. JWT подтверждения email дополнительно проверяется через одноразовое SHA-256-состояние в таблице `verification`, атомарно потребляемое при подтверждении. Токены не попадают в аналитику, журналы или клиентское хранилище.
- Проектные лимиты: 5 попыток входа за минуту, 3 запроса писем за минуту для регистрации, восстановления и подтверждения, отдельно для каждого endpoint; хранение rate limit — PostgreSQL через Better Auth. Без `AUTH_TRUSTED_PROXY_HEADER` запросы делят loopback-ключ лимита: это консервативный локальный режим. Для production можно задать имя одного заголовка с IP через `AUTH_TRUSTED_PROXY_HEADER`, только если origin доступен исключительно через доверенный proxy, который перезаписывает этот заголовок и не пропускает присланное клиентом значение. Не включать настройку при доступном напрямую origin. Проверить определение IP и поведение нескольких процессов перед production.
- Формат, границы значений, текущая сессия и принадлежность изменяемых данных повторно проверяются сервером. Возврат после входа допускает только разрешённый внутренний адрес.
- Доступ к БД, SMTP, ключ Better Auth и будущие OAuth secrets — только серверные переменные окружения. Не помещать их в `NEXT_PUBLIC_*`, клиентский bundle, URL, логи или примеры.
- Яндекс ID, Telegram и Kick — следующий этап с настоящими ключами и отдельной проверкой протоколов. Сейчас кнопки скрыты и соответствующие OAuth endpoints не подключены; имитации внешнего входа в приложении нет.
- Темы и интерфейс следуют `tokens.css`. Ручное предпочтение темы сохраняется локально, исходное следует системе. Приложение использует готовые тематические SVG и локальный Rubik с preload.

## Проверка

Автотесты, тестовые фреймворки и постоянные проверочные скрипты пока запрещены. После изменений выполнить подходящие typecheck и сборку, вручную проверить главный путь, ошибку и восстановление. Для доступа: регистрация → письмо → подтверждение → вход → обновление защищённой страницы → выход; неверный пароль; восстановление и отзыв старой сессии; недействительная ссылка; отказ SMTP; отказ в прямом доступе без сессии. Для интерфейса проверить обе темы, 320/768/1024 px, клавиатуру, фокус, reduced motion и меню аккаунта. Фактически непроведённые проверки явно отмечать в отчёте; этот список сам по себе не является результатом проверки.

Текущее окружение за HTTPS: `BETTER_AUTH_URL=https://a1d.by`. Сам процесс слушает 127.0.0.1:100; открывать вход через https://a1d.by/app/auth. Cookies Secure и trusted origin следуют HTTPS-адресу; localhost не является дополнительным origin. Для отдельного локального режима вернуть BETTER_AUTH_URL из .env.example и зарегистрировать отдельный localhost callback в Google.


Способы входа в настройках: сервер читает только providerId записей текущего пользователя, без токенов и хешей пароля. POST /link-social разрешён только для настроенных провайдеров, требует сессию Better Auth, возвращает в настройки. allowDifferentEmails=true разрешает явную привязку сервиса с другой почтой после успешного OAuth; профиль, включая основную почту, не перезаписывается (updateUserInfoOnLink=false). Идентичность, уже привязанную к другому пользователю, переносить нельзя. Автоматическая привязка при входе по-прежнему требует совпадения почты и requireLocalEmailVerified=true. Состояние OAuth-ожидания использует CSS opacity 320 мс и press 160 мс, reduced motion до 100 мс; сеть и навигация не задерживаются.


## Начальный фокус всплывающих окон — 2 ноября 2026 года

При открытии любого всплывающего окна, меню, диалога или боковой панели начальный фокус получает только нейтральный контейнер либо заголовок с tabindex="-1" и data-popup-focus, без видимой рамки. Само открытие не фокусирует кнопки и поля, не открывает вложенные подсказки, не выделяет текст, не вызывает экранную клавиатуру и не меняет значения. Не вызывать blur и не отключать фокус глобально: Tab/Shift+Tab и явная навигация стрелками сохраняют видимый фокус элементов, подсказки по намеренному фокусу/наведению/касанию работают. Модальные окна удерживают фокус внутри; Escape, закрытие и возврат к триггеру сохраняются. Tooltip и уведомления сами фокус не получают.


## Адаптивная навигация оболочки

Пункты основной навигации сразу открывают содержимое выбранного раздела. На телефоне используется нижнее меню, на планшете — панель по кнопке, на десктопе — sidebar. Основные разделы «Запустить / Мои запуски» не дублировать вкладками в рабочей области. Внутри профиля на всех ширинах сохранять локальные вкладки «Настройки / Оплата»: меню аккаунта открывает выбранную вкладку и скрывается, после чего вкладки позволяют переходить между подразделами без повторного открытия меню. В основных разделах вкладки профиля не показывать. Заголовок, адрес и активное содержимое соответствуют выбору; при переходе из меню фокус получает заголовок, при переключении локальных вкладок фокус остаётся на вкладке. Соблюдать равные доли ширины, иконки, видимые подписи, клавиатурные стрелки и crossfade 440 мс (reduced motion до 100 мс). Вкладки авторизации сохраняются.

На телефоне 320–767 CSS px левое меню заменяется только нижним: «Запустить», «Мои запуски», «Ещё». Боковая панель, кнопка «Меню» и дублирующая кнопка аккаунта в шапке отсутствуют; аккаунт, оформление и настройки открываются из «Ещё» снизу. На 768–1023 px остаётся панель по кнопке, от 1024 px — sidebar. При смене типа навигации открытые меню закрываются, фокус не возвращается к скрытому триггеру. Сохранять safe area, нижний резерв контента, видимый клавиатурный фокус и нейтральный начальный фокус popup. [Контракт](design/mobile.md).

## Запустить — 3 ноября 2026 года

С 4 ноября 2026 года ссылки YouTube `/shorts/<id>` распознаются как `shorts`. Канонический адрес Shorts сохраняется в результате и списке недавних; oEmbed и публичная страница запрашиваются по `watch?v=<id>` с прежними ограничениями. Вкладка канала `/@handle/shorts` остаётся канальной ссылкой; обычный адрес видео и сокращённая ссылка не определяют формат Shorts сами по себе. Для Shorts доступен расчёт просмотров по существующей демонстрационной цене.

Новым заданием разрешена замена «Тестовой 1» разделом «Запустить» (`/app?tab=one` сохраняется). Ссылка определяет Twitch/YouTube/Kick; корректная вставка сразу загружает публичные сведения, ручной ввод подтверждается кнопкой. Над демонстрационным списком услуг показаны полученные название, автор/описание/обложка, если доступны, исходный ID и составной идентификатор platform:kind:id (не номер заказа). Ключей API нет: YouTube использует oEmbed; Twitch/Kick — метаданные публичной страницы, которые могут отличаться от текущего эфира либо отсутствовать. Состояние live, просмотры, длительность и прочая неполученная статистика не выдумываются. Недоступность не считается отсутствием эфира. Повтор и изменение ссылки доступны. Цены, реальные заказы, исполнение и списание средств не входят в эту задачу; radio-выбор демонстрационной услуги показывает предварительное описание.

POST /api/stream-info требует подтверждённую серверную сессию и собственный Origin, ограничен 20 запросами в минуту на аккаунт через существующую таблицу rate_limit. Строгий парсер допускает только известные формы ссылок и строит канонический HTTPS URL без пользовательских query, порта и реквизитов; redirect запрещён, ответ ограничен 1,5 МБ, вход — 4 КБ. Таймаут площадки 10 с, клиента 15 с; смена ссылки/раздела отменяет запрос, устаревший результат игнорируется. Cookies Chrome использованы только для просмотра примера пользователем разрешённого StreamSkill; не переносятся на сервер или в исходники.

Миграция `0006_launch_catalog.sql` расширяет ограничения таблицы `launch_order`. Миграция `0007_streamskill_orders.sql` добавляет ID и статус поставщика; прежние записи остаются демонстрационными.

Ключ `STREAMSKILL_API_KEY` задаётся только в серверном окружении. Сервер сверяет [тарифы StreamSkill](https://api-docs.streamskill.pro/api-reference/endpoints/tariffs/all) через `GET /v1/tarifs`: таймаут 5 секунд, успешный ответ хранится 60 секунд. При отказе API каталог предлагает повторить загрузку; браузер не получает ключ или полный ответ поставщика.

`STREAMSKILL_LIVE_ENABLED=true` включает реальные заказы. Клиент видит итоговую цену YETI в USD; сервер отклоняет запрос, если подтверждённая клиентом сумма не совпала с расчётом. Базовые цены и ступени берутся из каталога YETI, без скидок или корректировок поставщика. Отображение баланса в реальном режиме использует подтверждённые пополнения и ручные корректировки за вычетом оплаченных заказов и резервов.

Под блокировкой аккаунта сервер сохраняет заказ и резервирует сумму до отправки [запроса создания](https://api-docs.streamskill.pro/api-reference/endpoints/purchases/create). Неопределённый ответ сохраняется для сверки; тот же заказ повторно не отправляется. Отказ создания или статус `refunded` освобождает резерв. Для подтверждённых заказов статусы читаются у StreamSkill. Действия паузы и смены региона доступны для демозаказов. У реальных заказов фолловеров Twitch есть отдельные действия запуска, остановки и настройки темпа.

API поставщика не документирует ключ идемпотентности или максимальную сумму в запросе создания. Расхождение со стоимостью поставщика не меняет цену, показанную клиенту. Резерв освобождают только после подтверждённого отказа или возврата; автоматически повторять покупку нельзя.

Реальный заказ использует тариф 220. При покупке отправляются логин Twitch, количество и интервал между подписками. Ползунок и числовое поле задают интервал от 10 до 43 200 секунд (12 часов) включительно с шагом 5 секунд. Начальное значение при покупке — 10 секунд. Сервер проверяет диапазон и шаг. Продолжительность не передаётся.

По кнопке «Запустить за …» сервер оформляет заказ, применяет выбранный разброс ±25% через [Edit Twitch Followers](https://api-docs.streamskill.pro/api-reference/endpoints/purchases/actions/edit-twitch-followers) и отправляет команду запуска. Карточка открывается в «Моих запусках» с последним подтверждённым статусом. Если разброс не подтверждён, заказ доступен для проверки настроек и ручного запуска. Для статусов `created` / `stopped` доступен ручной запуск, для `awaiting` / `working` — остановка. В этих же состояниях можно изменить интервал и разброс.

Миграция `0013_twitch_follower_start_check.sql` сохраняет время контрольной проверки новых реальных заказов. Через 30 секунд после создания фоновый обработчик Next.js запрашивает статус StreamSkill. Для `created` и `stopped` он отправляет одну команду запуска тому же заказу и сверяет статус. Для остальных состояний команда не отправляется. При ошибке чтения проверка доступна ещё 90 секунд. Ручной запуск или остановка в YETI отменяет ожидающую проверку. StreamSkill не сообщает, была ли остановка инициирована вручную в его кабинете, поэтому в коротком окне проверки такая остановка может привести к повторному запуску. Покупка и списание не повторяются. Миграцию нужно применить до запуска обновлённого процесса Next.js.

Сервер проверяет сессию, Origin, владельца и статус заказа. После команды запуска или остановки читает статус у поставщика. Миграция `0011_twitch_follower_settings.sql` сохраняет переданный при покупке интервал и подтверждённые настройки. Для старых заказов неизвестное значение остаётся пустым. API заказа не возвращает число доставленных подписок и текущие настройки: интерфейс показывает заказанное количество, статус и значения, сохранённые через YETI STREAM. Смена канала, аккаунтов исполнителя и удаление не выведены в кабинет.

Карточка фолловеров Twitch с известным интервалом показывает примерный прогресс по времени. Миграция `0012_twitch_follower_estimate.sql` сохраняет расчёт между посещениями. Отсчёт начинается при первом наблюдении статуса `working`, останавливается при выходе из этого статуса и продолжает накопление после возобновления. При смене темпа прежний участок учитывается по прежнему интервалу. До подтверждения `completed` оценка ограничена 99%. У уже работающих заказов расчёт начинается с первого обновления после миграции.
### Зрители Twitch: настройки заказа

В карточке заказа две отдельные кнопки: «Настройки зрителей» и «Управление чатом». Каждая открывает свой диалог. «Сохранить» отправляет заполненные поля открытого диалога, команды запуска и остановки чата отправляются отдельно. Интервал сообщений — целое число от 6 до 600 секунд включительно. Пустое поле оставляет интервал без изменений; форма ограничивает ввод, сервер отклоняет значения вне диапазона.

В «Моих запусках» настройки зрителей доступны для пакетов на час, сутки, неделю и месяц, пока заказ создан, ожидает, работает или остановлен. При неоднозначном ответе сервер перечитывает состояние и подтверждает действие только при совпадении. Кнопка меняется после подтверждения, а при ошибке позволяет заново проверить состояние.

## Ручные корректировки баланса

`/admin` открывается только для подтверждённой основной почты, указанной в серверной переменной `ADMIN_EMAIL`. Пустое значение закрывает доступ. Войти нужно через обычную форму `/app/auth`, затем открыть `/admin`. После изменения конфигурации перезапустить приложение.

«Пользователи» (`/admin?section=users`) показывает по 25 аккаунтов на страницу. Поля имени и email ищут буквальную подстроку без учёта регистра; ID сравнивается целиком. Заполненные фильтры объединяются через И, поисковые данные не помещаются в URL. Действие в последней колонке открывает свежий баланс и последние 20 корректировок пользователя.

Миграция `0008_true_kat_farrell.sql` добавляет журнал `balance_adjustment`. Поиск, чтение истории и запись повторно проверяют полномочия на сервере. В журнале хранятся пользователь, ID администратора, сумма со знаком в центах USD, причина, время и ключ операции. Повтор той же отправки не меняет баланс дважды. Если баланс успел измениться, сервер возвращает новый остаток для повторного подтверждения. Списание допускается в пределах доступного остатка с учётом резервов заказов. Корректировки входят в серверный баланс и не создают счета Heleket. В деморежиме пользовательский кабинет сохраняет согласованное временное отображение.

В действиях пользователя можно изменить имя и часовой пояс, заблокировать или разблокировать аккаунт. Блокировка отзывает существующие сеансы и запрещает новые, включая вход через OAuth. Администратор не может заблокировать или удалить свой аккаунт. Удаление с подтверждением доступно для аккаунтов без платежей, запусков и корректировок баланса. Оно удаляет профиль, учётные данные, сеансы и недавние ссылки. Аккаунт с историей можно заблокировать. Миграция `0010_admin_user_management.sql` добавляет проверку создания сеансов в PostgreSQL и журнал действий с идентификаторами пользователя и администратора, типом действия и временем.

## Коэффициент цен

«Общие» (`/admin`) сохраняет общий коэффициент от 0,01 до 100 с точностью до двух знаков. Миграция `0009_admin_pricing.sql` создаёт настройку со значением ×1. Коэффициент умножает базовый итог каталога до округления до цента; минимум платного заказа — 0,01 USD, бесплатный тест остаётся бесплатным. Настройка применяется к новым расчётам в реальном и демонстрационном режимах, не меняет суммы уже созданных заказов и не влияет на пополнение баланса. При изменении цены открытая форма обновляет каталог и требует повторного подтверждения. Сервер проверяет актуальность коэффициента также при резервировании средств. Сохранение настроек требует сессии администратора и своего Origin; конфликт редакций возвращает актуальный коэффициент. В таблице настроек остаются время и автор последнего сохранения.
