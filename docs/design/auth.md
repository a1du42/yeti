# Вход, регистрация и восстановление доступа

Дата: 2 ноября 2026 года. Контракт текущей email-авторизации на `/app/auth`, последующих внешних интеграций и локальной документационной [витрины](../../design-system.html#auth). Витрина остаётся демонстрационной; настоящее приложение и серверные процессы описаны в [инструкции разработки](../development.md).

## Текущая реализация

Next.js App Router + TypeScript, PostgreSQL + Drizzle и Better Auth. Реализуются email-регистрация с подтверждением адреса, вход, восстановление и защищённая оболочка `/app` с двумя тестовыми вкладками, данными и меню текущего пользователя. `/` пуст, `/admin` и `/partners` не реализуются.

Подтверждение email обязательно до входа. Новый пароль — от 15 до 128 Unicode code points, без обрезки/нормализации; сервер и клиент используют одинаковый подсчёт. Хеширование — поддерживаемый custom hash/verify Better Auth на асинхронном node:crypto.scrypt (N=131072, r=8, p=1, соль 16 байт) и timingSafeEqual, без нормализации. Стандартный хеш Better Auth заменён, поскольку применяет NFKC. Имя после trim не пустое, не более 120 Unicode code points; пароль trim не подвергается. Часовой пояс — проверенная IANA-зона. Сессии хранятся в PostgreSQL: скользящие 7 дней, обновление раз в сутки, cookie cache отключён. Ссылки подтверждения и сброса действуют 1 час; после сброса отзываются все сессии, автоматического входа нет.

Локально SMTP-письма поступают в Mailpit, без доставки на реальные адреса. Production SMTP и эксплуатационные настройки выбираются перед публикацией. Проектные лимиты Better Auth с хранением в БД: 5 попыток входа за минуту; 3 запроса писем за минуту для регистрации, восстановления и подтверждения. Это техническая настройка первого этапа, не обещание доступности почты.

Почта отправляется через Next.js `after()` после публичного ответа; интерфейс сообщает о принятии запроса и не подтверждает доставку. При ошибке SMTP журнал содержит только безопасное событие без адреса и токена; запрос можно повторить вручную. Устойчивой очереди и автоматических повторов пока нет. Лимиты действуют отдельно на endpoint; без `AUTH_TRUSTED_PROXY_HEADER` все запросы делят loopback-ключ. Настройку доверенного IP-заголовка включать лишь при закрытом прямом доступе к origin за proxy, который перезаписывает этот заголовок; [подробности](../development.md).

GET `/app/auth/reset` принимает reset token из ссылки, сохраняет его в HttpOnly cookie `yeti-reset` (path `/api/auth/reset-password`, SameSite Strict, Secure на HTTPS, HTTP только локально) и перенаправляет к форме с чистым URL. Cookie действует до 1 часа; срок и одноразовость самого токена проверяет Better Auth при смене пароля. Успех очищает cookie и отзывает все сессии. JWT подтверждения email дополнительно связан с одноразовым SHA-256-состоянием в таблице `verification`, которое атомарно потребляется при подтверждении. Ни обмен URL на cookie, ни открытие формы сами по себе не подтверждают действительность ссылки.

Google, Яндекс ID, Telegram и Kick — следующий этап с настоящими ключами. Сейчас кнопки скрыты и OAuth endpoints не подключены; описанный ниже внешний вход является контрактом будущей интеграции. Демо-флаги витрины не управляют доступностью сервисов приложения.

## Подтверждено пользователем

- Во входе: Google ID, Яндекс ID, Telegram через OAuth/OIDC, Kick, email и пароль. Сервисы отсутствуют в регистрации. Первый успешный вход через сервис автоматически создаёт аккаунт, если связанной идентичности ещё нет; повторный вход открывает существующий аккаунт.
- Обычная регистрация: обязательные имя, email, пароль и повтор пароля; без видимых пометок обязательности.
- После входа через провайдера **не требовать email**, если его нет в ответе. Не требовать пароль YETI STREAM для внешнего входа.
- Нужны форма запроса восстановления, состояние после запроса, переход по ссылке и форма нового пароля.
- VK ID, Apple, Twitch и passkeys ниже — рекомендации, не утверждённые интеграции.

Актуальный контракт ниже заменяет прежние варианты с третьей постоянной вкладкой, текстовыми кнопками сервисов и однократным вводом нового пароля.

## Состав форм и результат входа

| Сценарий | Что показывать | Результат |
| --- | --- | --- |
| Вход по email | Email, пароль, «Войти», «Не помню пароль» | Вход в существующий аккаунт после серверной проверки |
| Первый вход через сервис | Только на вкладке «Вход»: иконка настроенного провайдера | Проверка идентичности → автоматическое создание и привязка аккаунта → вход |
| Повторный вход через сервис | Та же кнопка во входе | Найти аккаунт по проверенной внешней идентичности и войти без повторного создания |
| Обычная регистрация | Имя, email, пароль, повтор пароля; определённая зона или select при неудаче определения | Проверить поля и продолжить email-регистрацию; кнопок сервисов нет |
| Восстановление | Единственная вкладка после «Не помню пароль»; email, затем новый пароль и повтор | После подтверждённой смены вернуться ко входу |

Обязательное имя относится к обычной email-регистрации. Не переносить это требование на первый внешний вход и не добавлять отдельную форму завершения регистрации после провайдера без новой задачи. Не считать совпадение email доказательством общей учётной записи: внешний аккаунт определяется проверенным идентификатором провайдера.

## Компоновка и доступность

Экран доступа `/app/auth` — самостоятельная компактная форма без навигации заказов, управления и партнёрства. Готовый логотип нужной темы, вкладки, способы входа, поля, основная кнопка и переход к восстановлению. После вкладок показывать заголовок панели: «Быстрый старт» во входе и «Создать аккаунт» в регистрации. Затем во входе — сервисы (или поля, если сервисов нет), в регистрации — поле «Имя». Подписи вкладок и кнопок действий сохранять. Без рекламной колонки, метрик и обещаний. Корневой `/` остаётся пустым. Витрина использует только якорь `#auth` и не занимает продуктовый маршрут.

Витрина показывает две равные вкладки «Вход» и «Регистрация» на всю ширину. После «Не помню пароль» их заменяет единственная вкладка «Восстановление» на всю ширину. «Вернуться ко входу» восстанавливает две вкладки и фокус входа. Каждая вкладка содержит Phosphor Regular и видимый текст; скрытая вкладка исключена из клавиатурного обхода. Стрелки, Home/End, Tab; crossfade 440 мс, reduced motion только opacity до 100 мс. Содержимое доступно сразу, неактивные панели inert и aria-hidden; высота области сохраняется за счёт общей Grid-ячейки. Это способ сравнить формы в документации; будущие ссылки из писем должны открывать нужный экран напрямую.

Карточка до 512 px, отступы 32 px / 16 px на узком экране; на телефоне от 320 CSS px иконка и полная подпись каждой вкладки стоят рядом в одну строку. Не ставить иконку над текстом и не переносить подпись. Для мобильных вкладок: Rubik 14 px, gap 4 px, горизонтальный padding 0; равные доли ширины и область нажатия не менее 44 px сохраняются. Это исключение из общего разрешения переноса длинных подписей вкладок. Rubik 400–700 загружается локально с preload. Только семантические токены; синяя основная кнопка. Кнопки сервисов показывают только фирменный цветной знак, названия доступны в tooltip и aria-label: Google и Яндекс из официальных ресурсов; Telegram (#26A5E4) и Kick (#53FC18) из Simple Icons (CC0). Брендовые знаки — исключение из палитры и Phosphor; интерфейсные иконки остаются Phosphor Regular. Перед интеграцией применить официальные правила кнопок и брендинга каждого провайдера; макет не заменяет официальный компонент входа Google.

У всех полей видимые label без пометок обязательности; required и проверка сохраняются, у ошибок aria-describedby и aria-invalid. Email — type=email, inputmode=email; вход — autocomplete=username/current-password; регистрация и новый пароль — new-password. Восстановление — autocomplete=email. Разрешены вставка, менеджеры паролей, пробелы и Unicode в пароле. Пароль не обрезать, не trim и не менять без действия. Глаз / перечёркнутый глаз Phosphor Regular — отдельная кнопка без видимого текста ≥44 × 44 px с доступным именем и aria-pressed. Изменение типа поля сохраняет введённое.

Проверка впервые при blur / submit, затем при исправлении; при одной ошибке фокус к полю, при нескольких — резюме со ссылками. Исправление не переносит фокус. Неизвестный аккаунт, неверный пароль и неподтверждённый адрес не различать публичным ответом входа. После реального подтверждения успеха — уведомление снизу по центру, role=status; вводные ошибки остаются у полей. Сетевой отказ не очищает введённое. Витрина явно называет любой успех демонстрационным.

## Сценарии

### Вход по email

1. Email и пароль → «Войти». Не применять правила нового пароля к существующему.
2. Отправка сразу, aria-busy и защита от повторного нажатия. При ошибке — «Не удалось войти. Проверьте почту и пароль или восстановите доступ».
3. После подтверждения сервера создать новую сессию и открыть допустимый экран запрошенной зоны. Возврат только на разрешённый внутренний адрес; прямые URL и операции повторно проверяют права на сервере.

### Регистрация по email

Имя, email, новый пароль и повтор пароля с проверкой совпадения. Имя — input type=text, autocomplete=name; пустое значение и строка из пробелов дают «Введите имя». Не требовать фамилию и не ограничивать имя только кириллицей или латиницей. Сервисы в этой форме не показывать. Несовпадение показывать у повтора; при исправлении любого из двух полей перепроверять совпадение без переноса фокуса. То же правило действует при восстановлении. Часовой пояс определяется через Intl.DateTimeFormat().resolvedOptions().timeZone; при неудаче или ошибке API показывается обязательный выбор IANA-зоны без предвыбранного значения. При успехе найденная зона видна рядом с формой; не подставлять Москву или смещение вместо неизвестной зоны. Показывать понятное русское название города или региона и текущее смещение UTC, например «Москва · UTC+03:00», вместо одного Europe/Moscow. IANA-идентификатор сохраняется значением данных; одинаковые подписи в ручном списке различаются дополнительным IANA-кодом. Смещение вычислять для выбранной зоны на текущую дату, учитывая сезонное время; не хранить одно смещение вместо зоны. Полное выбранное название повторять под select с переносом. Если смещение получить не удалось, явно указать это, не подставлять UTC+0. Список сортируется по русским подписям; для зон без локального названия города используется локализованное название часового пояса из Intl. Подтверждение адреса одноразовой ссылкой обязательно до входа в аккаунт. Общий ответ не раскрывает существование аккаунта: «Проверьте почту для продолжения регистрации. Если аккаунт уже есть, попробуйте войти или восстановить пароль». Перед реальным запуском нужны утверждённые документы условий и обработки данных и решение о требуемых согласиях. В витрине нет фиктивного checkbox согласия и ссылок `#` на несуществующие документы.

Действующая политика нового пароля: 15–128 Unicode code points; нет требований смешивать регистры/цифры/символы, вставка разрешена. Подсчёт согласован на сервере и клиенте, хеширование — описанный выше custom scrypt без нормализации. Не хранить пароль открытым и не отправлять внешним провайдерам. Проверка скомпрометированных паролей и MFA остаются отдельными открытыми решениями. Витрина показывает прежний демонстрационный минимум 15 символов; она не заменяет серверную проверку. Источник исходного предложения — [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).

### Вход через сервис с автоматическим созданием аккаунта

Кнопки только во вкладке «Вход»: Google, Яндекс ID, Telegram, Kick. Перед кнопками не показывать пояснение об автоматическом создании аккаунта; сама логика создания сохраняется. В будущем выбор ведёт к официальному провайдеру; обратный переход проверяется сервером до создания сессии. Для уже связанной идентичности — вход в тот же аккаунт. Для новой — автоматически создать аккаунт и связать внешнюю идентичность только после успешной серверной проверки. Не требовать перехода в обычную регистрацию, дополнительного email или собственного пароля. Не объединять с существующим аккаунтом по совпадению email. Создание и привязка должны быть атомарны и защищены от дублей при повторном/параллельном callback. При отмене или ошибке аккаунт не создаётся. Условия и требуемые документы до запуска остаются открытым вопросом. В витрине это локальное состояние, внешний сайт не открывается.

Email, если возвращён провайдером, не становится автоматически подтверждённым резервным способом входа. Для восстановления через почту и назначения собственного пароля нужен отдельный подтверждённый процесс привязки. Отсутствие email не блокирует вход. При потере единственного внешнего аккаунта без резервного способа почтовый сброс недоступен: восстанавливать доступ у провайдера. Процесс исключительного восстановления службой поддержки пока не определён; не обещать его в интерфейсе.

Отмена разрешения — нейтральное состояние с возможностью повторить или выбрать другой способ. Недоступность сервиса не отключает остальные способы. Не скрывать кнопки по IP или предполагаемой стране и не обещать доступность во всех странах; это проверяется перед запуском для целевых регионов.

### Восстановление пароля

1. «Не помню пароль» → единственная вкладка «Восстановление» → email → «Отправить ссылку». Для аккаунтов без email видна инструкция повторно войти через связанный сервис.
2. Одинаковый публичный ответ для известного/неизвестного адреса и аккаунта только с провайдером: «Если для этого адреса доступно восстановление, придёт письмо со ссылкой. Проверьте входящие и спам». Не раскрывать наличие учётной записи кодом ответа или заметной разницей времени. Повторная отправка доступна с серверным ограничением частоты, без выдуманного таймера в UI.
3. Одноразовая ссылка с криптографически случайным токеном, ограниченным сроком и серверной проверкой. Хранить проверочное представление токена, не открытый токен; не записывать в журналы/аналитику. URL восстановления не содержит email; токен допускается только в предназначенной одноразовой ссылке и после обмена удаляется из адресной строки. Не строить адрес письма из непроверенного Host; на странице сброса исключить сторонние ресурсы и передачу токена через Referer.
4. Неверная, истёкшая или использованная ссылка: «Ссылка недействительна или уже использована. Запросите новую». Не давать изменить пароль без действующей серверной проверки, не блокировать аккаунт из-за запросов восстановления.
5. Новый пароль и повтор нового пароля → проверка совпадения → «Сохранить пароль» → сервер подтвердил → сообщение и возврат ко входу. Отозвать все действующие сессии; после сброса не входить автоматически. Уведомление о смене пароля — отдельное дальнейшее улучшение почтового процесса.

Требования основаны на [OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html). Действующие сроки, локальная почта и проектные лимиты определены в разделе «Текущая реализация»; production SMTP выбирается перед публикацией.

## Доступность и расположение сервисов

Сервер проверяет полный комплект обязательных настроек провайдера. Если ключи или другие необходимые настройки отсутствуют, кнопку сервиса не выводить. Клиент получает только публичные признаки доступности; ключи и секреты остаются на сервере. Запрет действует также на прямой запуск OAuth и callback: одного скрытия кнопки недостаточно.

Кнопки расположены только во входе и показывают только фирменные знаки. Каждой задать доступное имя «Продолжить через …», tooltip с тем же действием по наведению/фокусу/касанию, видимый фокус и область минимум 44 × 44 px. Не полагаться на title. Иконка сохраняется при ожидании и после результата.

Не более четырёх кнопок в ряд. При 1–3 сервисах они заполняют ряд равными долями; при 4 — четыре равные кнопки; при 5+ сохраняются ширина полного ряда и центрирование неполного последнего ряда. При нуле сервисов скрыть группу и разделитель «или по электронной почте»; email-форма остаётся доступной. Длинные доступные имена не должны влиять на геометрию.

Витрина демонстрирует настройку через authProviderAvailability в showcase.js и checkbox «Подключённые сервисы (демо)». Это признаки примера, а не настоящая конфигурация интеграций. Изменение флагов отменяет текущее ожидание; сброс возвращает Google, Яндекс ID, Telegram и Kick. Память первого/повторного входа — только локальный Set по демонстрационному сервису, без реальных идентификаторов; сброс и перезагрузка её очищают.

Источники встроенных знаков: [Google G](https://developers.google.com/identity/images/g-logo.png), [Яндекс](https://yandex.ru/favicon.ico), [Simple Icons](https://github.com/simple-icons/simple-icons) для Telegram/Kick; [лицензия CC0](assets/SIMPLE-ICONS-LICENSE.txt). Знаки скрыты от скринридера, доступное имя задаётся кнопке; фирменные цвета сохраняются в обеих темах.

## Контракт провайдеров для будущей интеграции

| Способ | Протокол и идентификатор | Минимальные данные и границы |
| --- | --- | --- |
| Google | Google OIDC, серверная проверка ID token; ключ issuer + sub | Для входа достаточно openid и нужного профиля; email не обязателен. Не запрашивать YouTube scopes для обычного входа |
| Яндекс ID | OAuth Authorization Code + PKCE S256; серверный профиль и стабильный id | Минимальные права профиля; почта не обязательна. Не предполагать, что OAuth access token сам является ID token |
| Telegram | OIDC Authorization Code + PKCE S256; issuer + sub | Регистрация бота и Allowed URLs через BotFather. Не запрашивать phone и право сообщений бота ради входа |
| Kick | OAuth 2.1 Authorization Code + PKCE S256; серверный GET /public/v1/users и user_id | user:read для идентичности текущего пользователя. Не использовать app token для доказательства входа и не требовать email |
| Email + пароль | Собственная серверная проверка подтверждённого адреса и хеша | Локальная идентичность отделена от внешних; пароль, токен сброса и сессия не попадают в клиентское хранилище |

Общие требования: зарегистрированные точные redirect URI, одноразовый state, привязка state/PKCE verifier к инициировавшему браузеру и операции, короткий срок попытки. Для OIDC — nonce и проверка подписи через ключи провайдера, issuer, audience, exp и nonce; для OAuth-only Яндекса/Kick — получать профиль сервером с полученным user token. При несовпадении проверки сессию не создавать. Код обменивать на сервере; client secret и долгоживущие токены остаются на сервере. Сессия — защищённая HttpOnly/Secure cookie с подходящей SameSite-политикой; CSRF и ротацию выбирать со стеком. Не хранить внешние токены в localStorage. Повторный callback не создаёт второй аккаунт.

Привязка дополнительного провайдера — только из подтверждённой сессии с повторной проверкой владения, явным действием и защитой от уже занятой внешней идентичности. Нельзя отвязать последний рабочий способ входа. Самостоятельная регистрация не выдаёт доступ к `/admin` и не зачисляет в `/partners`; каждая зона отдельно проверяет права.

YouTube использует сервер авторизации Google. Вход в Google не доказывает право управлять конкретным каналом, особенно при нескольких каналах и Brand Account. Подключение канала, выбор канала и YouTube API permissions — отдельная задача после выбора услуг; в текущем входе они не запрашиваются. Аналогично вход Kick не даёт права молча выполнять операции с каналом.

Официальные материалы, проверенные 2 ноября 2026 года: [Google OIDC](https://developers.google.com/identity/openid-connect/openid-connect), [YouTube OAuth](https://developers.google.com/youtube/data/guides/authentication), [Яндекс: code + PKCE](https://yandex.ru/dev/id/doc/en/codes/code-url), [Telegram Login](https://core.telegram.org/bots/telegram-login), [Kick OAuth 2.1](https://docs.kick.com/getting-started/generating-tokens-oauth2-flow), [Kick Users](https://docs.kick.com/apis/users.md), [Kick scopes](https://docs.kick.com/getting-started/scopes.md). Повторно сверить API и брендовые требования перед интеграцией.

## Что ещё рекомендовано

Это продуктовая оценка соответствия аудитории, не статистика распространения и не гарантия региональной доступности.

| Вариант | Где полезен | Приоритет и причина |
| --- | --- | --- |
| VK ID | Россия и часть аудитории СНГ | Следующий региональный кандидат; официальный [VK ID Web SDK](https://github.com/VKCOM/vkid-web-sdk) |
| Sign in with Apple | Аудитория Apple в США и других странах Америки | Следующий международный кандидат. Веб-настройка требует Services ID и связи с primary App ID приложения с Sign in with Apple; проверить возможность регистрации команды и условия до обещания интеграции. [Настройка Apple](https://developer.apple.com/help/account/capabilities/configure-sign-in-with-apple-for-the-web/) |
| Twitch | Владельцы стриминговых каналов разных регионов | Сильное соответствие продукту, но отдельное решение. Вход не равен подключению управления каналом. [Twitch OIDC](https://dev.twitch.tv/docs/authentication/getting-tokens-oidc/) |
| Passkeys | Все целевые регионы при поддержке устройством | Дополнительный способ после создания аккаунта; не зависит от выбранной соцсети. Нужны отдельные сценарии добавления, потери устройства и восстановления. [FIDO](https://fidoalliance.org/passkeys/) |

Рекомендуемый порядок обсуждения: VK ID, Apple, Twitch; passkeys следующим этапом улучшения входа. Не добавлять сразу все кнопки. SMS не предлагается как базовый способ: потребуются отдельные бюджет, поставщики, доставка и защита от злоупотреблений. Email остаётся независимым вариантом; доступность почтовой доставки тоже требует проверки. СНГ и Америка неоднородны: перечень стран, языки и фактическую доступность провайдеров уточнить перед запуском, не выводить региональную поддержку из наличия OAuth.

## Как проверить витрину

1. Открыть `design-system.html#auth` локально или [на порту 100](http://127.0.0.1:100/#auth). Ничего не устанавливать.
2. Пустой вход → резюме двух ошибок, ссылки к полям. Неверный email → ошибка формата. Исправить, проверить кнопку глаза и вставку вымышленного пароля.
3. «Результат следующего действия»: отказ и ошибка соединения → отправить → значения остаются; переключить на успех → повторить. Во время 650 мс нажать повторно, изменить поле, переключить вкладку или отменить: старый ответ не должен появиться.
4. Во входе Google, Яндекс, Telegram, Kick → первый успех показывает автоматическое создание аккаунта; повторный успех того же сервиса показывает вход в существующий. После сброса снова первый вход. В регистрации кнопок сервисов нет. На чистом примере проверить отмену, отказ и сетевую ошибку: следующий успешный внешний вход всё ещё должен считаться первым. После второго успеха проверить отсутствие повторного создания. В настоящей интеграции это серверный результат, в витрине — только демонстрационное состояние.
5. Регистрация → пустое имя и имя из пробелов → «Введите имя» → исправление → короткий пароль → исправление на ≥15 символов → несовпадающий повтор → исправление. Проверить автоматический часовой пояс: понятное название и актуальное смещение UTC. «Часовой пояс не определён (демо)»: пустой select даёт ошибку; варианты имеют понятные подписи, выбор зоны снимает ошибку и повторяет полное название ниже. Проверить зону с дробным смещением и зону с сезонным временем; value остаётся IANA-кодом. Отправить → ответ о письме → «Подтвердить адрес (демо)». Для недействительной ссылки выбрать соответствующий результат **до отправки**.
6. «Не помню пароль» → единственная вкладка восстановления → email → одинаковый ответ без проверки существования → «Открыть ссылку из письма (демо)» → новый пароль и его повтор → ошибка несовпадения → исправление → демо-успех → ко входу. Выбрать недействительную ссылку до отправки и повторить запрос с успешным сценарием.
7. Отключать сервисы по одному: 4 / 3 / 2 / 1 / 0, проверять равные доли и отсутствие группы при нуле; проверить имена кнопок и tooltip клавиатурой. При расширении списка до 5+ отдельно проверить центрирование последнего ряда. Сбросить пример: поля, ошибки, результаты и показ пароля возвращаются к исходным значениям. Перезагрузка также очищает данные; только предпочтение темы сохраняется общим механизмом витрины.
8. Обе темы, 320 / 375 / 414 / 768 / 1024 / 1440 px, zoom 200%, Tab/Shift+Tab, стрелки/Home/End и reduced motion. Полные подписи, видимый фокус и отсутствие горизонтального обрезания.

Фактический отчёт — [verification.md](verification.md). Чек-лист не означает, что все пункты уже пройдены. Автотесты не добавлять.
